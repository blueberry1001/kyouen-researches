# 9×9 misère の資源制限付き探索

2026-10-03。9×9 空盤の misère 勝敗を追加調査した記録である。
**勝敗は未決定 (`UNKNOWN`)**。以下の有限資源で終了した探索を、先手勝ち・後手勝ちの根拠には用いない。
1×1〜8×8の確定結果は [既存ノート](game-structure-20261003.md) を参照。
ここで misère は「最後の合法手を打った側の負け」を意味し、合法手が0個の局面は手番側の勝ちとする。

## 探索基盤

既存の `cpp/solvers/kyouen_dfpn_root.cpp` は81点を扱えるが、
通常ルールでの終端処理が OR/AND 展開、厳密終盤解法など複数箇所に存在する。
今回の短い資源枠では、8×8で検証した misère 専用 DFS と
「合法点6個以下の完全な安全部分集合族」への縮約を81ビットへ移植した。
通常ルールの勝敗キャッシュや証明書は流用していない。

実装は [game_structure_20261003_nine.cpp](verification/scripts/game_structure_20261003_nine.cpp)。
盤面と合法手集合に `__uint128_t` を使い、上位47ビットを盤外として扱う。
各着手後の8個の D4 像を更新し、その最小値を占有集合の代表とする。
着手で新しく禁止される点は、着手点と既置石2点を含む禁止4点集合から求める。

メモのキーは、代表占有集合の点番号を

\[
0\le p_1<\dots<p_k\le80
\]

としたときの可逆な組合せ順位

\[
R(S)=\sum_{j=0}^{k-1}\binom{81}{j}
      +\sum_{i=1}^{k}\binom{p_i}{i}
\]

である。固定した (k) で後半が (k) 点部分集合の colex 順位となり、
前半が異なる点数の順位区間を分離する。

\[
\sum_{j=0}^{20}\binom{81}{j}
=6\,837\,944\,227\,813\,170\,424<2^{63}
\]

なので、20点以下のキーは64ビットに厳密に収まり、全ビット1の空スロット標識とも一致しない。
21点以上をキー化しようとした場合は、切り詰めず `UNKNOWN` で停止する。
この上限は幾何学的な最大石数の主張に依存しない。

スロット数は201,326,611。占有キー8バイトと勝敗ビットを持ち、探索中の保存局面上限は130,000,000。
小終盤キャッシュは完全な安全部分集合ビットマスクをキーにし、最大2,000,000種類まで保存する。
このキャッシュが満杯でも、その後の小終盤は正しく直接計算する。
時間上限・メモ上限・順位の定義域超過は例外を根まで伝播させるため、
未解決の祖先を負け局面としてメモ化しない。
時間は16,384回の再帰呼出しごとに検査するため、指定時刻は検査間隔分の超過を許す。

空盤が内部的に解けた場合も、完全な通常着手に展開した証明書を出力するまでは探索完了としない。
展開後も出力は `independently_verified:false` とし、別の証明書検査なしに勝者を確定しない。
今回の試行はその段階に到達していない。

## 独立した部品検査

[Python検査器](verification/scripts/game_structure_20261003_nine_validate.py) は、
探索器の座標を平行移動した3×3式とは別に、元の4×4行列式を二乗距離の列で余因子展開する。
全 \(\binom{81}{4}=1,663,740\) 組を列挙し、禁止4点集合29,152個を一致確認した。
これには4点共線と4点共円の双方が含まれる。

固定種20261003から生成した1,000安全局面について、全禁止4点集合を直接走査し、次を検証した。

- 合法手集合を既置石から再構成し、逐次更新した集合と一致。
- 座標の回転・反射で独立計算した D4 代表が一致。
- Python の任意精度整数による組合せ順位が一致。
- 合法点6個以下の412局面で、全禁止4点集合から直接作った残余制約による再帰勝敗が一致。

上位64ビット側に既置石を含む標本は793局面、標本中の最大既置石数は17。
これは実装の部品検査であり、空盤の勝敗証明ではない。

別担当の独立監査でも、円・直線6,814個から生成した禁止4点集合、同じ1,000局面、
412終盤の再帰勝敗が一致した。20石の最大順位、bit80の扱い、盤外bit81と21石の拒否も確認した。
さらに、公開ソースの作業用コピーだけを3×3・4×4・5×5へ切り替え、
出力証明の28・232・2,308局面の全閉包を独立幾何から検証した。
根の結果は順に後手勝ち・先手勝ち・後手勝ちで、既知結果と一致した。
公開した再現監査では、9×9で保存上限1局面または期限 \(10^{-9}\) 秒を指定し、
いずれも終了コード2の `UNKNOWN` となることを確認する。
監査用の作業コピーだけでスロット数を4,000,037（キー配列約32 MB）に減らしており、
元の探索ソースは変更しない。

[独立監査ハーネス](verification/scripts/game_structure_20261003_nine_audit.py) と
[順位・盤外ガード検査](verification/scripts/game_structure_20261003_nine_audit_domains.cpp)、
[監査結果JSON](verification/game_structure_20261003_nine_audit.json) を保存している。
独立した監査全体は次の単独コマンドで再現できる。

```sh
python research/verification/scripts/game_structure_20261003_nine_audit.py \
  --output /tmp/kyouen-nine-audit.json
```

## 試行結果

初手優先順位を中央 `(4,4)` と角 `(0,0)` に変え、別々の空メモから試行した。
両方とも130,000,000局面の保存上限に達し、終了コード2、結果 `UNKNOWN`。
いずれも証明書は生成されなかった。

| 最優先の初手 | 探索時間（秒） | 小終盤評価回数 | 小終盤の種類数 | 最大 RSS（KiB） |
|---|---:|---:|---:|---:|
| 中央 `(4,4)`、点40 | 327.773 | 356,457,570 | 567,281 | 1,630,660 |
| 角 `(0,0)`、点0 | 320.808 | 355,973,432 | 571,526 | 1,630,840 |

時間上限はそれぞれ800秒と440秒で、いずれも時間上限より先にメモ上限へ達した。
2試行の探索時間合計は約649秒、最大 RSS は約1.67 GBだった。
機械可読結果は [中央優先のJSON](verification/game_structure_20261003_nine_center.json) と
[角優先のJSON](verification/game_structure_20261003_nine_corner.json) に保存している。

## 再実行

リポジトリのルートから次を実行する。
出力される時間や RSS は環境依存であり、再現時に同じ値を要求しない。
再現器は中断・異常終了も `UNKNOWN` として記録し、探索完了だけの場合も `UNVERIFIED` として記録する。

通常のCIは `check_game_structure_20261003.py --nine-only` に相当する軽量な標本検査だけを行い、
以下の9×9空盤探索を実施しない。

```sh
python research/verification/scripts/game_structure_20261003_nine_reproduce.py \
  --work-dir /tmp/kyouen-nine-center-repeat \
  --output /tmp/kyouen-nine-center-repeat.json \
  --seconds 800 --opening 40

python research/verification/scripts/game_structure_20261003_nine_reproduce.py \
  --work-dir /tmp/kyouen-nine-corner-repeat \
  --output /tmp/kyouen-nine-corner-repeat.json \
  --seconds 440 --opening 0
```

メモや証明書などの大きい一時ファイルをリポジトリへ収録する必要はない。
保存JSONは明示的なソース3ファイルと標本列の SHA-256 を持つ。
今回の結果は、このアルゴリズム・着手順・資源上限で未解決だったという記録に限られる。
一般に9×9の厳密判定が困難であるという下界も、いずれかの勝者も主張しない。
