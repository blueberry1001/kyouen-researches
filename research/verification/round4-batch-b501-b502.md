### 実装の自己検査（`--selftest`）

boost が WSL に無く sudo も使えないため多倍長整数は**自作**（base 10^9 リム）である。
この自作 bigint が壊れていれば DP 全滅するため、`unsigned __int128` と突き合わせる
単体テストを `--selftest` として内置した（加算・減算・乗算・小整数乗算・除算と余り
（8 ケース、全リム検証）・gcd・既約分数化・20 桁小数の厳密展開）。
**`bigint selftest: PASS (0 failures)`**。

この検査で実際にバグを 2 種検出した（いずれも DP のホットループに波及するもので、
検査が通的前提下でなければ n=6 の「一致」は得られなかった）:
1. `bn_divmod` が商バッファの `wa` リムしか初期化せず、呼び出し側が全リムを読むと
   **スタックの未初期化ゴミを読む**。DP の gcd 簡約の商と `frac_str` がこれに当たった。
   → 全商バッファをゼロ初期化する `bn_div` ラッパに統一。
2. `dec_str` が商を受け取らず分子をそのまま出力していた（`5162.000...`）。
   → 商バッファ接收に修正。

## 1. C++ 実装（`scripts/round4_b501_prand.cpp`）

- 共有コア `kc_core.h` の `build_square(n)` を使用（書き直していない）。
- 状態 = 盤の `uint64` マスク（n=7 は 49 点で収まる）。層ごとにソート済み配列。
- 列挙: 層 k の各状態の合法手マスクを O(F) の禁止4点組パスで求め、
  `occ|(1<<v)` を層 k+1 に二分探索。重複はソート+unique で除去。
  （合法手マスクは辺に沿って単調でない — u を置くと w が新たにブロックされうる —
  ので O(F) パスを省略しない。第3回と同じ判断。）
- Grundy: 子の g を `uint64` のビット集合に OR して mex（最下位 0 ビット）。
- p_rand: 層ごとの共通分母 `D_k`（多倍長整数）で厳密に。`cnt = |L(S)|` は
  常にその層の lcm `Lk` を割るので、`Lk/cnt` を先に計算すれば**大整数除算は不要**。
  `num_k = (cnt*D_{k+1} - Σ子) * (Lk/cnt)`、層ごとに gcd で簡約。
- メモリ: **隣接 2 層の分子のみ保持**。最大層でも n=7 は約 1,800 万状態で
  分子は 4 リム（36 桁）前後なので数百 MB 程度。
- 並列化: `-fopenmp` で 16 コア。辺の走査・Grundy・分子計算・閾値カウントを並列化。

n=6 の実測: build 0.06 s / enumerate 18.96 s / solve 434.79 s = **合計 453.75 秒**。
Python の 129 秒より遅いのは、Python 版が numpy で層ごとベクトル化しているのに対し
本 C++ は状態ごとの多倍長整数 `bn_add` が支配的なため。うち n=6 の k=7 層
（1,783,296 状態・11,674,336 辺）が約 254 秒を占めた — この層の `D_k` が 18 桁と
比較的大きく、分子への 4 リム加算が全辺で走るのが原因。n=7 ではこの層が
10 倍規模になるため、**残存する性能ボトルネックはここ**（下記 2 に到達状況を記載）。

### 棄却した高速化（記録に残す）

層ごとの gcd 簡約を「並列ブロック畳み」にした版が一度採用されたが、
**block ごとの partial gcd を 1 ではなく D_k から始めている**ため統合結果が
小さくなり、n=4 で P_max = 0 という明白な壊れ方をした（n=5 でも 2383/3360 が 1 になる）。
gcd は結合的なので畳み自体は可能だが partial の初期値を 1 にする必要がある。
正しさが見えるまで戻した（現在は逐次畳み、初期値 D_k、早期 break）。

# 第2節：n=7 の完全走破（**1,225.64 秒 / 20 分 26 秒**）

上のボトルネック（多倍長整数の4リム加算）は実測では問題にならなかった。
**n=7 は 1 億 7981 万状態・14 億 9354 万辺を完走した。**

前回（第4回前半）の走行が exit 137（OOM kill）で中断したが、原因は
**WSL の 19 GB を他エージェントと共有していた**ためである。
単独実行ではピーク RSS 10.5 GB で収まり、完全に走破した。

## 2.4 残った問い

- **p_rand の最大値の漸近上限**。0.56296 (n=4) → 0.70923 (n=5) → 0.78035 (n=6)
  → 0.80281 (n=7) と単調増加して **0.8 付近で飽和しかけている**。
  n=8 が 2 億 8 千万状態で 10 GB 超のメモリを要するため、n=8 の完走は
  現環境（19 GB）では困難。ただし層構造から n=8 の最長層は
  約 1.4 億状態と見積もられ、**1 状態あたりのメモリを 1/2 に減らせば可能**。
- 3/4 超の割合が n=6 で 4/126万、n=7 で 124/4126万と**ともに減少傾向**。
  絶対数は増えるが割合は薄くなる。極限で 0 になるかどうかは未判定。
