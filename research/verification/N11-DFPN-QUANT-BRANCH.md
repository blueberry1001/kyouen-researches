## 先行する記述の訂正（2 点）

### 1. 量化の向き

二石 root について:

- 証明: `∃m3 : ∀m4 : ∃m5 : WIN`
- 反証: `∃m4 : ∀m5 : LOSS`

**ある m3 を反証するのに「全 m4 について全 m5 が LOSS」である必要はない。**
1 つの m4 の全 m5 が LOSS ならその m3 は捨てられる。
コードの `if(!found) break;` はその打ち切りであり正しい。

ただし **m4 は OR ノードなので、ある m4 を反証するには
合法な m5 を全て LOSS と証明する必要がある。**
「最初の数個の五手目が LOSS だった」だけでは m4 は反証されない。
先行文書がここを「数個で LOSS に到達した」と書いていたのは誤りで訂正した。

### 2. 計算量の上界

| 意味 | query 数 |
|---|---:|
| 1 つの m3 を WIN と証明する最悪 | 117 × 116 = 13,572 |
| 1 返信全体の素朴な絶対最悪（m3 約 119 個） | 119 × 117 × 116 = 1,615,068 |

LOSS な m3 は「ある m4 の全 m5 が LOSS」で終了するので、
実測 query 数はこれより桁違いに少なくなり得る。

## 観測 1: oracle root cache は 0 hit、重複 key なし

6 query すべて異なる canonical key であり、`hits=0`。
**異なる m5 が同一 s5 局面になることは少なくともこの範囲では無い。**
したがって root cache は短絡の主要因にならない。

## 観測 2: deep TT による再利用は劇的に効く（最重要）

**q=6 が 1 node で完了した。**

`tt_used` が q=5 の 16,676,488 から **1 ノードも増えていない**。
つまり q=6 の s5 局面は**既に main PnTT に解として入っていた**。
前 5 query の exact 探索（約 2,030 万 nodes）が内部状態を書き込んでおり、
q=6 はそれだけで即答できた。

これが「root cache hit 率では分からない reuse」の正体である。
`nodes/query` の推移がこれを 直接示す:

```
3,932,058 → 4,920,863 → 3,320,924 → 4,384,707 → 3,733,015 → 1
```

**最初の数 query で構造が TT に蓄積され、その後はほぼ無料になる。**

## 観測 3: 6 query すべて LOSS

最初の 6 個の s5 がすべて LOSS だった。
m4 は OR ノードなので、これは**まだ m4 を反証した証拠にならない**が、
残りの五手目も LOSS である可能性はある。
もしそうなら m3 は 6 query 级的的成本で反証できる。

**実測 query 数がこれ以上進まなかったため、
この推測は検証できていない。**

## 打ち切り理由

30 分の wall allowance 中に q=7 の `[q-start]` まで進んだが
`[q-done]` が出ず、task 側が終了させた。
**q=7 単体が異常に重かった**可能性がある
（前 5 query は 3.3〜4.9M nodes / 21〜47 秒に対し、
q=6 の 1 node は異常値なので q=7 も同じ TT を引くextent は分かる）。

query 内の watchdog（4096 nodes ごとに quant deadline を確認）は
入れてあるが、**終了が正常系でなかったため
その経路が実際に発動したかは未確認**。

## 結論

1. **TT 再利用は支配的である。** root cache は 0 hit だが、
   deep TT により 6 個目の query が 1 node で済んだ。
   したがって「query 数が爆発する」という懸念は
   **同一 TT を共有する場合杞憂**である。
2. **1 送信の query コストは指数的に減少しうる**ため、
   最悪値 1,615,068 query からの時間見積もりは悲観的すぎる。
3. 次の測定は「**m3 を何個試したか**」「各 m4 は SAT/REFUTED/UNKNOWN のどれか」
   を longer 集めること。ただし q=7 の単发重さは先に調べる必要がある。

## 追測: memo 2^24 vs 2^26（q7 の原因切り分け）

同一 reply 0、他条件同一（node budget 20M/query、allowance 1500 s）。

| 指標 | memo 2^24 | memo 2^26 |
|---|---:|---:|
| 完了 query 数 | 57 | 49 |
| total nodes | 253,651,240 | 187,798,134 |
| 100 node 未満の query | 2 | **5** |
| avgprobe 最初 → 最後 | 1.153 → **27.06** | 1.031 → **19.95** |
| 1 query 当りの最大 evict_solved | 7,196,788 | 7,063,762 |
| 最終 tt_used | 16,777,216 / 16,777,216 | **67,108,864 / 67,108,864** |
| 非自明 query の平均 ms | 26,921 | 30,922 |
| 結果 | 57 件すべて LOSS | 49 件すべて LOSS |

### 結論 1: q7 の異常は TT 飽和と整合する

2^24 では q5 時点で 16,676,488 / 16,777,216 = 99.4% となり、
以降 `ttused=16777216/16777216`（**完全満杯**）で確定した。
`es`（evict_solved）が query の nodes と同値になっている =
**その query で確保した全エントリが solved 枠から追い出された**ことを示す。
avgprobe は 1.15 から **27.06** へ伸びている。

**これはprobe 長大化であり、probe 上限（PROBE=32）に近い。**
したがって 2^24 では「已被 evict された solved entry を
 TT の外から付け外し」する。q7 の長時間化は
**局面難度ではなく TT 飽和による探索の劣化**と整合する。

### 結論 2: ただし 2^26 も飽和した

予想と異なり、2^26 でも `ttused=67108864/67108864` に達し、
avgprobe は 19.95 まで伸びた。したがって
**容量を 4 倍にしても 1 返信の 49〜57 query の範囲では足りなかった**。

差異は以下:

| | 2^24 | 2^26 |
|---|---|---|
| 100 node 未満の query | 2 | 5 |
| total nodes | 253.7M | 187.8M |
| 平均 ms | 26.9 s | 30.9 s |

2^26 は**同等の query 数に対して nodes が 26% 少なく**、
かつ**無料 query が 2→5 に増えている**。つまり容量拡大は
**効果はあるが制約を解いてもいない**。

## 結論 2 の解釈（慎重に）

1 返信あたり約 50 query × 平均 400 万 nodes = 約 2 億 nodes で
飽和に達する。2^26（6,700 万 entry）では 1 query あたり
約 30 万 entry を確保することになり、飽和は必然的である。

**したがって「TT 拡大で回避できる」見込みは弱まった。**
本筋は cut-based oracle だが、
50 query / 返信で 2 億 nodes なら 20 返信で約 40 億 nodes
（約 13 時間 @5e5 nodes/s）で**回せる計算量**ではある。

## 次の手への示唆

1. **cut-based oracle を検討すべき段階に来ている。**
   TT 拡大では 4 倍で足りず、probe 劣化が構造的な障壁である。
2. ただし**まず 1 返信を閉じる**ことを優先する。
   50 query × 2 億 nodes で 1 返信は到達可能かもしれない。
   二石 root が 1 個でも閉じれば、20 返信に拡張する意味が出る。
3. m4=REFUTED が出てもいないので、
   現在の m4 消費は全て SAT 方向（WIN 探し）か UNKNOWN 方向の可能性がある。
   branch telemetry の三値集計がこれを明確にする。

## soundness 修正（最重要）

### 1. quant_solve の最終判定が誤証明し得た

三値化のあとも最後が `return saw_unknown ? 0 : 2;` だったが、
**`saw_unknown` は初期化されるだけで一度も true になっていなかった**。
したがって全 m3 を走査し終えた場合、途中に UNKNOWN な m3 があっても
**LOSS を返していた**。これは誤証明である。

修正: 最終判定を `q_m3_unknown_` を見る形にした。

```
if(q_m3_unknown_>0) return 0;
return 2;
```

`q_m3_unknown_` は m3 ごとに局所的に立てる
（`m3_unknown` → `++q_m3_unknown_`）。
「flag が立っていない」ことに依存する判定をやめた。

### 2. q_m4_sat_ が常に 0

`q_m4_sat_` はゼロ_clear されるだけで、
`found` のところで `++` されていなかった。
`telemetry 上は常に 0` になっていた。
`if(found){ ++m4_sat; ++q_m4_sat_; continue; }` に修正。

### 3. timeout query の計測落ち

`catch(QuantTimeout)` が即 `return -1` していたため、
その query が消費した nodes / wall / TT growth / eviction / probe が
**すべて集計から落ちていた**（= 毎 run の最後の query）。
共通 finalize を通すようにし、`[q-timeout]` 行を出すようにした。

## s4 direct exact vs m5 列挙 A/B

`∃m5 : WIN(s5)` は s4 局面が OR ノードなので
**「その s4 局面を exact に解く」ことと等価**。
これを `--s4-ab=r2,m3,m4` で実装し、
同じ局面・同じ budget・同じ memo で 2 方式を比べる。

対象: quant が最初に到達する局面（r2=0, m3=1, m4=最古の合法手）。

| budget | memo | arm | result | nodes | ms | queries |
|---:|---:|---|---:|---:|---:|---:|
| 20,000,000 | 2^24 | direct | UNKNOWN | 20,000,000 | 101,723 | 1 |
| 20,000,000 | 2^24 | enum_m5 | UNKNOWN | 20,000,000 | 82,021 | 1 |
| 100,000,000 | 2^26 | direct | UNKNOWN | 100,000,000 | 596,986 | 1 |
| 100,000,000 | 2^26 | enum_m5 | UNKNOWN | 100,000,000 | 488,710 | 1 |

**両 arm とも最初の 1 query で budget を使い切る。**
20M でも 100M でも、`enum_m5` は `queries=1` しか進んでいない。

### 解釈

この s4 局面は**集中精査した s5 より難しい**。
s5 は 1 件あたり 330 万〜490 万 nodes で解けていたが、
**s4 を exact に解こうとすると 20M では 1 query も終わらない**。

したがって「s4 を exact に解けば ∀m4 が安くなる」という期待は
**この測定では裏切られた**。m5 を 1 個ずつ s5 oracle に投げる方が、
同じ budget ではるかに多くの m5 を検査できる。

**理由の推測**: s4 を exact に解くと、
その下の全ての s5 を**まとめて**解こうとするため、
1 個の WIN m5 を見つけるために 100 万 nodes 規模の s5 を
多数まとめて解くことになる。
一方 m5 を 1 個ずつ投げれば、
既に TT に答えがある s5 は 1 node で終わり、
無いものだけ 330 万 node かかる。

**これは「win を見つけるのが goal」であって
「その m4 が WIN か LOSS かを完全に分類するのが goal」ではない**
という目的の差であり、実用上は前者が有利である。

## 現時点の判断

**「s5 を 116 個ずつ呼ぶ」方式を維持する。**
s4 direct exact はこの測定では感度が低く、各 m5 をまとめて解くため
途中結果を失う。

ただし **s4 direct は「その m4 が LOSS であることの証明」が必要な
m3 の反証経路には依然有用かもしれない**。
そこは今回の測定では未確認。

## 次にすべきこと（更新）

1. **s4 direct A/B を budgets 差で取り直す**（100M で enum_m5 の
   何 query 進んだか）。20M では両方 1 query しか進んでいないため
   比較として不十分。
2. **s5 の budget を 10M から上げた場合の m5 消費**。
   s5 bench では 10M で s5 全件が閉じた。

   m5 oracle の 1 件あたりは確実に閉じ、
   その情况下で s4 direct が勝つ可能性がある。
3. **二層 cache（s6〜s8 のみ永続）**。TT 拡大ではなく
   「何を永続化するか」に移る段階。
