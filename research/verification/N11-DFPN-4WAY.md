# df-pn 4点比較（各15分・fresh process・fresh TT memo=26）

実行: 2026-09-29〜30。`dfpn --n=11 --reps --memo=26 --only=V --budget=900`。
回帰試験: n=4 LOSS（239 expans）、n=5 WIN（847）、n=6 WIN（55,561）、
n=7 LOSS（2,123,417、18秒）で既知勝敗と完全一致。

## 前提の修正（重要2件）

**修正1: 子 TState の canonical 再構築バグ。**
初版の df-pn は無限ループしていた（n=4 で visited=2.5億・expanded=108 凍結）。
原因は、子局面の TState を canonical key から再構築していたこと。
canonical は8つのD4像の最小値なので、key のビットパターンは一般に
**回転像**であり、手を指して到達した局面ではない。回転 occupancy から
計算した `added_bans` は親フレームの `legal` と不整合で、子は TT エントリと
一致しない phantom position を探索し、bounds が永久に収束しなかった。
子 TState を親 Gen バッファから直接コピーする修正で解決。

**修正2: second minimum の定義（今回）。**
初版は「全子が同値なら second-best なし（b2=-1 → INF閾値）」としていたが、
これは非標準で、1個の子をほぼ解き切るまで掘り続ける DFS 的挙動になる。
しかも生成順依存で同値多重集合が 1 にも INF にもなった。
標準形（**同値込みの真の second minimum**）に修正:
best 選択の tie-break（合法手数・key）はそのまま、runner-up は pn/dn の
多重集合から取る。子 `(1,1,1,...)` なら閾値は `min(parent, 2)` になり、
「子の数が2になったら親へ戻れ」が働く。
depth guard も `>256 pop` から **`>V+8 throw`** に変更（合法ゲームは
V 手を超えないので、それ以深はバグとして大声を上げる）。

## 読み取り

1. **根は初期値から動いている**: 一石局面は AND node で子は全て (1,1)。
   初期値は子数そのもの（中央20・角65・辺65・一般119）。
   前回は15分後もこの値のままで「収束」と誤読したが、今回は
   pn=20→94,599（中央）、dn=1→18,941 のように**両方とも大きく動いた**。
   これが標準閾値での真の15分スナップショット
2. **両方増えるのは正常**: df-pn の初期 pn/dn は楽観的下界（全子1）。
   探索が進むと真の値に近づくが、真の値自体が大きい局面では
   両方が増加する。pn/dn の時系列（hb行）が単調に一方向へ寄るかが
   次の判断材料。今回は hb 行の永続化に失敗し時系列なし
3. **中央が最も収束方向**: pn=94,599 は他（20万超）の半分以下。
   ただし桁の差ではなく、スクリーニングには21点全走が必要
4. **展開効率**: 15分で約860〜1,180万展開。DFS の 2.5〜2.8億 visited とは
   単位が違う（展開=TT新規登録、visited=再訪含む到達）ため単純比較不可

## 残課題

- hb 行（root pn/dn 時系列）の永続化: 今回 `--log` 先が `build11/logs/`
  に変わったが、hb 行自体がファイルに出ていない。heartbeat の gate
  （5秒かつ2^20）が原因の可能性。次走では gate を緩めて時系列を確保
- 21点スクリーニング（各5〜10分）で pn の小さい順にランク付け
- 有望株に長時間集中し、pn→0（P証明＝先手勝ち証人）を狙う
