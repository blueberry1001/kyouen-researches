# 専用 quant solver: 2 石 root を ∃m3 ∀m4 ∃m5 で解く

**11x11 の勝敗は UNKNOWN のまま。**
本ファイルは**実装と途中経過**であり、勝敗の断定ではない。

- base commit: `cd86ea7`
- 実装: `cpp/solvers/kyouen_dfpn_root.cpp`
- 機械: WSL / g++ -O3 -march=native、16 cores / 19 GB RAM
- swap 使用 0

## 出发点: 二石 root の論理的構造

二石 root `{m2,r2}` は OR ノードである。したがって
**「元为先手が勝つ」を示すには、勝つ三手目が 1 つあればよい**。
三石局面は AND ノードなので、選んだ三手目に対する
**全ての四手目**で WIN を維持しなければならない。
四石局面は OR ノードなので、各四手目について
**勝つ五手目が 1 つ**あればよい。

```
二石 root r2  =  ∃m3 : ∀m4 : ∃m5 : s5(m2,r2,m3,m4,m5) が WIN
中央初手全体  =  ∀m2 : ∃m3 : ∀m4 : ∃m5 : s5 が WIN
```

記録した 23 個の s5 root は 10M nodes 以内で解けることが分かっているので
（`N11-DFPN-S5-BENCH.md`。**これは df-pn が L72 で選んだ 23 局面について
の測定であり、任意の s5 局面についての普遍的事実ではない**。
実際、quant が後から出した別の m5 からは 100M nodes でも閉じない s5 が
存在した）、残るのは 3 段の量化評価だけである。
汎用の exact DFS で二石 root を直接解くと、この構造を捨ててしまう。

**注意: 「二石 root を閉じるには全ての子が証明される必要がある」
という記述は誤り。** WIN を示すには 1 つの勝つ三手目で十分であり、
 ∀ が必要なのは「勝つ三手目を選んだ後」の四手目に対してだけである。

## 実装

`--quant-first=60 --quant-replies=... --quant-budget=N [--quant-timeout=S]`

- `s5_oracle()`: 正規化 key → WIN/LOSS の永続 cache 付きで
  5 石局面を exact で解く。**UNKNOWN は cache しない**
  （budget 切れを後続のより豊かな query が引き継いでしまうため）。
- `quant_solve()`: `∃m3 : ∀m4 : ∃m5 : s5 WIN` を直接評価。
- `quant_root()`: oracle cache を保持したまま 1 返信を処理。
- driver `run_quant()`: 20 返信を**単一 process**で回すので
  cache が返信間で共有される。異なる三手目・異なる返信が
  同じ D4 軌道の s5 局面に到達するため效果があると期待する。

### 証明書

WIN が出た場合のみ、次の形式で出力する:

```
reply r2
  winning third move r3
    for every legal fourth reply r4
      a winning fifth move r5 and the canonical key of that s5
```

20 返信すべてでこれが出れば、中央 `60` が P 局面であることの
直接証明になる。某一返信で全三手目が失敗すればその返信は反証。

## 開発中に見つけた自分のバグ

`--quant-*` の 4 つのフラグすべてで `substr()` のオフセットが
1 ずれていて、空文字列や `=60` を `stoi` に渡して `error: stoi` に
なっていた。フラグ名長 + 1 が正解である
（`--quant-replies` は 15 文字なので 16 から取る）。

**このような mistake は「その経路を初めて通ったとき」にだけ露見するため、
フラグを追加するたびにオフセットを機械的に検証すべき。**
既存のフラグをすべて検証したところ、他は正しかった。

## 撤回: 「予算が 2〜3 桁不足」という結論

この結論は**誤り**であり、撤回する。理由は 2 つある。

1. **`--quant-budget` は query ごと**に与えられる（20M/query）。
   当初は「三手目全体で共有する 20M」と読み、
   `20M / 13,572 = 1,473 nodes/query` と計算したが、この計算は
   コードと一致していない。
2. **`queries=0` は「query が始まっていない」ではない。**
   進捗行が oracle 呼び出しの**前**に出され、次の行が
   **最初の query が戻るまで**出ないため、
   止まった `queries=0` は「1 つ目の query がまだ終わっていない」
   という意味に過ぎなかった。

いずれもテレメトリ不足から生まれた解釈であり、**測る前に
結論を書くべきではなかった。** 正しい測定は
`N11-DFPN-QUANT-FIRSTQ.md` に記録した。

## 量化の向き（重要）

二石 root について:

- 証明: `∃m3 : ∀m4 : ∃m5 : WIN(s5)`
- 反証: `∃m4 : ∀m5 : LOSS(s5)`

**ある m3 を反証するのに「全 m4 について全 m5 が LOSS」である必要はない。**
m3 の反証条件は `∃m4 ∀m5 LOSS` であり、
**1 つの m4 の全 m5 が LOSS であることが分かれば m3 は捨てられる。**
コード本体の `if(!found) break;` はその 1 点を打ち切る実装であり正しい。

なお m4 は OR ノードなので、
**ある m4 を LOSS と証明するには合法な m5 を全て LOSS と証明する必要がある。**
「最初の数個が LOSS だっただけでは m4 は反証されない」。
先行する文書の記述がここを逆に書いていたため訂正した。

## 計算量の上界（整理）

| 意味 | query 数 |
|---|---:|
| 1 つの m3 を WIN と証明する最悪 | 117 × 116 = 13,572 |
| 1 返信全体の素朴な絶対最悪（m3 約 119 個） | 119 × 117 × 116 = 1,615,068 |

ただし LOSS な m3 は「ある m4 の全 m5 が LOSS」と分かった時点で終了するので、
**実測 query 数はこの最悪値より桁違いに少なくなり得る。**
したがって最悪値から時間を見積もるのではなく、
**m3/m4 ごとの短絡率を測る**のが正しい順序である。

## correctness

- hybrid 回帰: n=4 LOSS / n=5 WIN / n=6 WIN / n=7 LOSS（不変）
- adaptive 回帰: 全条件 pass（不正指定は rc=2）
- quant は n=11 専用の実装（5 石固定）のため、
  n=6/7 では「二石 root を 3 段量化で解く」こと自体が
  正しい比較対象にならない。quant の soundness は
  **n=11 で 1 返信を閉じて certificate を出力できるかどうか**で
  判定する（certificate は第三者が再検証可能な形になっている）。

## 次にすべきこと

1. **短絡率を測る**（最悪値からの時間見積もりではなく）。
   m3 を何個試したか、各 m3 で m4 を何個試したか、
   各 m4 が SAT / REFUTED / UNKNOWN のどれで終わったかを記録する。
   多数の m3 が「1 個の m4 の全 m5 LOSS」で早期脱落するなら、
   13,572 query/m3 という最悪値はほとんど無関係になる。
2. **再利用が効いているかを nodes/query で見る**。
   root cache の hit 率だけでは不十分で、publish=ALL なので
   exact_prop が内部 solved state を main PnTT に書いており、
   2 個目以降の query が内部 TT 共有で大幅に進む可能性がある。
   1. **D4 縮約には注意が必要**。117 個の m4 が大幅に減るのは
   三石局面に非自明な stabilizer がある場合だけで、
   一般の三石配置では対称性がほぼ消える。
   したがって 117 → 十数個への縮約は前提に置いてはいけない。
