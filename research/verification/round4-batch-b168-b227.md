## 途中で見つけた実装上の重要な誤り（自分の実装の記録）

第4回の C++ ソルバを最初に書いたとき、Grundy 値を**ボトムアップ**
（k=0 から上向き、g(∅)=0 を初期値）で漸化させていた。
正しい漸化は `g(S) = mex{ g(S ∪ {p}) : p 合法 }`、`g(終端) = 0` で、これは
**トップダウン**（k=K から下向き）で計算しなければならない。
ボトムアップだと `g({p}) = mex{0} = 1`、`g(∅) = mex{1} = 0` という
**偽の不動点**が得られ、全ての単独石に g=1 を渡して `W_n = ∅` になってしまう
（`g(∅)` は自由変数ではない。終端層の値から決まる）。
本回の C++ はトップダウンに直し、`g0 = 1,1,0,1,1`（n=2..6）、
`W_5 = {2,6,8,10,12,14,16,18,22}`（9 点 = 市松色 - 角、PROTOCOL と一致）で
**PROTOCOL の確定値を再現した**。
なお `round3_chunk3_core.py` の `solve_pn` / `solve_gn` はメモ化再帰
（`ev(occ)` が到達性で下降）であり本来就トップダウンなので、
先行ワーカーの実装自体にはこの誤りはない。

- 前回の一手: 「『K 損失が非零で加法的』例は n≤5 に無いため、主張の前半は未検証。後半 (g の非加法) は成立。」
- 今回の範囲: 4×4 の全 **120 組**の二点削除の各行について、K 値と g 値を**厳密に**集計した。
- 証拠:
  - **K について**: 120 組**すべて**で `K_pair = K_full = 7`。すなわち
    **一点削除でも二点削除でも K は 7 のままで、K の損失は常に 0**。
    120 組すべてで `K_loss_additive = true`（0 = 0 + 0 は自明に加法）。
  - **g について**: **12 組**で `g_combo_effect = true`。すなわち
    g の変化が**単独削除の値から読み取れない**。
    具体例（4×4, id = 4y + x）:
    - 削除 (0,0)+(3,0) = id {0,3}: g_full = 0, g_{一点0} = 0, g_{一点3} = 0, **g_{二点} = 2**
    - 削除 (0,0)+(2,2) = id {0,10}: g_full = 0, 一点で 0, 0, **二点で 2**
    - 削除 (1,1)+(2,1) = id {5,6}: g_full = 0, 一点で 0, 0, **二点で 2**
    すべて **g: 0,0 → 2** で、**単独では何も変わらない 2 つの削除の合成でだけ g が動く**。
  - 120 組中の g 値の種類は {0, 2} の 2 値のみ（`g_pair` の unique = {0, 2}）。
- 残った障害: 主張の**前半**「K 損失が**加法的**」は**確認**したが、
  **「K 損失が非零である」部分が n≤5 で一度も起きない**ため、
  **容量と戦略の乖離を「非零の容量損失つき」で示す例は不在**。
  今回観測されたのは **容量（K）が不動なのに戦略値（g）が動く**という、
  主張の「容量には相互作用がない」側を支持する現象である。
  ただし「容量が**減る**二点」という条件付き部分は未検証。判定は PARTIAL。
