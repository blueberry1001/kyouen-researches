## 2. 【最重要】Codex に証明してもらった 6 件

**B141 の判定訂正**が最大の成果。**前の記録が誤っていた**。

ファイル: [`round4-collinear-asymptotic.md`](round4-collinear-asymptotic.md)
独立検証: [`ROUND4-B141-VERIFICATION.md`](ROUND4-B141-VERIFICATION.md)

### 証明された定理

`n×n` 格子の共線四点組数を `D_n` とすると

\[
D_n = \frac{7\zeta(2)}{60\zeta(3)}\,n^5
      - \frac{3}{4\zeta(2)}\,n^4\log n
      + O(n^4)
\]

主項定数は `7ζ(2)/(60ζ(3)) ≈ 0.15965`。

### 何が間違っていたか

**第1回**は `D_n/(n^5 ln n)` が n=28〜40 で 0.0323 に安定することから
`D_n = Θ(n^5 log n)` と結論し、B141 を **REFUTED** にした。

**これが誤読だった。** 対数が現れるのは n^4 次の補正項であって主項ではない。

根本原因: 原始方向 v の寄与は `D_v(n) = Σ_{t≥3} C(t-1,2)(n-at)(n-bt)` で
`D_v(n)/n^5 → (5-3r)/(120H³)`（H = max(a,b)、r = min(a,b)/H）。
方向ごとの減衰が **H^{-3}** なのに方向本数が **O(H)** なので、
方向の和は **Σ H^{-2} 型の収束級数**になり、対数を生成しない。
第1回はこれを ΣH^{-2} と誤認していた。

### 検証方法（独立に再現済み）

三つの独立に導いた方法で D_n を数え、**n=4..11 で完全一致**：

| n | 外積全走査 | 有限和 (4) | 最大線分 C(ℓ,4) 和 |
|---:|---:|---:|---:|
| 4 | 10 | 10 | 10 |
| 5 | 64 | 64 | 64 |
| 6 | 234 | 234 | 234 |
| 7 | 660 | 660 | 660 |
| 8 | **1,524** | **1,524** | **1,524** |
| 9 | 3,156 | 3,156 | 3,156 |
| 10 | 5,928 | 5,928 | 5,928 |
| 11 | 10,428 | 10,428 | 10,428 |

n=8 の D_n = 1,524 は既知の確定値（PROTOCOL.md の F_8 = 14,564 のうち共線分）。

主項定数も有理数区間で確認:
φ を 200,000 までふるいで `Σ_{H≤L} φ(H)/H³` を厳密に評価、
尾部 ≤ `1/L` で評価して
`0.159650136 < 7ζ(2)/(60ζ(3)) < 0.159650719`。
原記録の区間 `0.159649781 < c < 0.159650948` を内包し矛盾しない。

再現: `python research/verification/scripts/verify_b141_independent.py`

## 6. 【最優先・未完】n=8 の p_rand

**ここが次に着手すべき唯一の大きな目標。**

### 現状

- n ≤ 7 は**完全に解けている**（上表）
- n=8 は**未完**。WSL 再起動で列挙が中断された
- ログ: `/tmp/stream.log`（再起動で消失）、spill は `/tmp/lk_8/`（消失）

### 重要な訂正（現在の見立て）

`round4-n8-feasibility.md` は「層成長が 32 倍、n=8 は 19 GB で不可能」と書いたが、
**この見積もりは 12 倍過大評価だった**。実測で判明した正しい理解:

**真の障害は「層成長」ではなく「ソート/重複除去の作業メモリ」**。

既存の `enumerate_levels` は
```cpp
std::vector<u64> nxt(est);      // est = 辺の数（層サイズの約 8 倍）
for (...) nxt[cur[v]++] = ...;  // 全部入れる
std::sort(nxt.begin(), nxt.end());   // 辺数分をソート ← ここが瓶颈
nxt.erase(unique(...), ...);
```

`est` は層サイズではなく**辺の総数**。n=8 の k=7→8 では
`nxt` だけで数 GB、ソート作業メモリがさらに要す。

### 解法（実装済み・n=6, n=7 で検証済み）

`scripts/round5_prand_stream.cpp` に **v-max 分割**による層生成を実装。

```cpp
// 子集合を「追加点 v の列」に分割する。ただし v が子の最大点であることを要求:
C'_v = { S ∪ {v} | S ∈ L_k, v ∈ L(S), S < 2^v }
```

- (i) `C'_v` 同士は**互いに素**（子の最大点は一意に v）
- (ii) 任意の `T ∈ L_{k+1}` は `v = max bit(T)` により**ちょうど一度**生成される
- (iii) `C'_0, ..., C'_63` を昇順に連結すると**ソート済み配列**になる

→ **sort も unique も不要**。層サイズ `M` 個だけを生成すればよい。
さらに **spill してディスクに落とす**ことで、ピーク RAM が層サイズに無関係に一定。

## 7. CRT 版ソルバの制約（重要）

`scripts/round5_b501_prand8.cpp` は分子を **mod 2^61−1** で持つので
1 状態 8 B（vs 大整数版 97 B）で速い。

- n=6: ピーク 0.34 GB
- n=7: ピーク 13.43 GB、646 秒（大整数版 1,226 秒より速い）

**構造的には n=6, n=7 で正しい**（状態数・辺数・P 局面数・最大値の層が一致）。

**ただし閾値カウント（1/2, 2/3, 3/4 超）は信用できない。**
分母 `D_k` が 61 bit を超えると `3*num > 2*D` の比較が剰余で壊れる。

n=6 の `P_gt_2_3` は CRT が 244、参照が 180（P 局面の 99% 以上が
D_bits 152〜607 の不正確な層にいる）。`P_gt_1_2` と `P_gt_3_4` の一致は偶然。

**教訓**: 閾値統計が必要なら多倍長整数に sacrificing に戻すこと。
`round5_crt_bug.md` に詳細。

## 11. 失敗から学んだこと（次のワーカーへ）

1. **100 ターンで強制終了される。** 「全部読み終わってから書く」は必ず成果ゼロになる。
   **最初に空ファイルを作り、ID ごとに逐次追記すること。**

2. **WSL のインラインコマンドは PowerShell のクォートで壊れる。**
   長いスクリプトは必ず `.sh` に書いてから実行。
   stdout が空に見えるときはファイルへリダイレクトすること。

3. **メモリを他エージェントと共有している。** WSL は 19 GB 全体を共有。
   重い計算を他のエージェントと同時並行すると exit 137（OOM）になる。
   **重い計算は単独で走らせること。**

4. **交差検証を飛ばすと結果が壊れる。** 新しいソルバは n=4, 5, 6, 7 の
   既知値と**必ず**突き合わせてから使うこと。
   CRT 版で `P_gt_2_3` がずれたのは、閾値比較の精度上限を
   気づかなかったため。

5. **ASan は必須。** `round5_b501_prand8.cpp` で 4 つの実際のバグ
   （numk2 の範囲外書き込み、levels の解放オフバイバイ、hidx の範囲外、
   バッファサイズの不一致）を ASan が見つけた。

6. **ガードを入れる。** レベルの解放のように「静かに壊れて exit 0」になる
   パターンがあるので、`if (levels[k].size() != expected) exit(6)` のような
   明示的な検査を入れること。
