# n=8 メモリ実験 — 実測レポート

作成: 2026-09-28。作業: 共円ゲーム (kyouen) n=8 の p_rand ソルバのメモリ実験。

**結論（先に）**: n=8 の層成長は「32 倍」ではなく **7.4 倍**だった。
`round4-n8-feasibility.md` の 18 億状態という見積もりは **12 倍過大評価**であり、
*n=8 は 19 GB の箱で実行可能* と実測で確認した。障碍は「層成長」ではなく
**ソート/重複除去の作業メモリ**にあった。

**`/tmp` は WSL の ext4 仮想ディスク（939 GB 空き）で、宿主の D: drvịve ではない。**
したがって spill 先としては `/tmp` を使う。**`/mnt/d` は 11 GB しかなく、
n=8 の全層（数百 GB 規模）すら置けない。** spill 先を `/mnt/d` にすると
失敗するのは容量のせいであり、メモリのせいではない。

**重要**: 作業ディレクトリが `/mnt/d` にあるので `/tmp` と `/mnt/d` は別の
ファイルシステムである。spill 専用ディレクトリは `/tmp` に作ること。

## 3. すべてが遅くなる元凶は「ソート」だった

### 既存コード（`round5_b501_prand8.cpp` の `enumerate_levels`）

```cpp
std::vector<u64> nxt(est);          // est = 層 k+1 への「辺の数」
for (...) nxt[cur[v]++] = A[i] | (1<<v);
std::sort(nxt.begin(), nxt.end());  // 辺数分 (!) をソート
nxt.erase(unique(...), ...);       // その後重複除去
```

`est` は層サイズではなく **|L_k| の平均次数倍の「辺の総数」** である。
n=8 の k=7→8 では edges ≈ 850,000,000 なので **`nxt` だけ 6.8 GB**、
ソートは作業メモリをさらに要し、**`unique` 前の要素数 8.5 億が
`nxt` に全て保持される**。これが「32 倍成長」に見えた正体である。

### 解説: ソート不要の層生成（v-max 分割）

子集合を「追加点 v の列」に分割する。ただし **v が子の最大点**であることを要求する:

```
C'_v = { S ∪ {v} | S ∈ L_k, v ∈ L(S), S < 2^v }
```

このとき:
- (i) `C'_v` 同士は**互いに素**（子の最大点は一意に v になる）
- (ii) 任意 `T ∈ L_{k+1}` は `v = max bit(T)` により**ちょうど一度**生成される
- (iii) `C'_0, C'_1, ..., C'_63` を昇順に連結すると**ソート済み配列**になる
  （`C'_v` の全要素は `2^{v+1}` 未満、`C'_{v+1}` の全要素は `2^{v+1}` 以上、
   同一 `C'_v` 内では `S ↦ S∪{v}` は大小関係を保つ）

**結果**: 層 `k+1` は**ソート済み・重複なし**で、**`|L_{k+1}|` 個**の要素として
直接生成される。sort も unique も不要、ソート対象は層サイズの `M+1` 個だけ。
計算量は `O(|L_k| + E_k)`、作業メモリは **`8 × (|L_k| + |L_{k+1}|)` バイト**
（in-RAM の場合）。spill 出力なら `8 × |L_{k+1}|` バイトのファイル 1 つだけ。

## 7. 各案の判定

### 案1: 層を「ソート済み v の列」で持つ — **打ち切り妥当**

指示書の推測どおり `u24` インデックスは **18 億状態を表現できない**ので
案1は成立しない。`u32` インデックスは 4 B × 1.82e9 = 7.3 GB、
さらに「追加点列」（1-2 B/state）に hashtable が要るので **20+ GB**。
**判定: 打ち切りが妥当。** 数値:
- 状態数 1.82e9 × `u32` index 4 B = 7.3 GB（=u24 では 5.5 GB だが 2^24 超過で不可）
- さらに値本体と hashtable を読むと 20 GB 超で **19 GB を超える**

### 案2: 全層保持をやめて spill する — **正解。これが n=8 を可能にした**

実装済み。`enumerate` と `solve` の両方で**ピーク RAM が層サイズに無関係**に
一定（n=6 でも 0.28 GB、n=8 でも 0.27 GB 程度）。spill 先は `/tmp`（939 GB）。
**判定: 採用。これが正解。**

### 案3: 1 層ずつ再生成して捨てる — **案2と同等 Acquivalent、spill 优于**

指示書の議論（「層 k-1 は層 k の全状態から 1 bit を削除したものだが重複になるので
集合化が必要 → 18 億状態をソートして unique → 28.8 GB で不足」）は正しい。
しかしこの**再生成 orientation は「子 k+1 から親 k を作る」**Directions であり、
Actual に layer k を reverse 生成するには layer k+1 の全状態を保持して集合化する
必要があり、案2（spill）に适さない。

**正しい orientation**: p_rand の DP は k を**降順**に処理するので、
$k$ の値から $k-1$ の値を計算するには**$k-1$ の親**が必要で、
親は**子（$k$）から生成**される。したがって 1 層再生成は
**forward 生成（k から k+1）**の方であり、これは案2で既に解決済み。
**判定: 案2が案3の上位実装。案3単独では不十分（集合化の 28.8 GB で破綻）。**

### 案4: 上から-reduction — **効かない（指示書の判断が正しい）**

最大値 `P_max` だけなら全状態の値は必要に見えるが、
「どの状態が最大か」を決めるには全状態を走査してその値を知る必要がある。
Grundy `P/N` 判定も全状態の grundy 値が必要。
**判定: 案4は効かない。ただし per-level maximum は
「1 層分の値だけあれば決まる」ので、案2 なら問題ない。**

## 8. 1 層保持の理論計算と実測の乖離

指示書の想定:
> 「8 B/状態 × 18 億 = 14.4 GB」が箱に収まるなら 1 層保持で理論上可能

**実測: 層成長は 7.4 倍（18 億の予測に対して 8.5 千万程度）。**
つまり 8 B × 最長層 = **0.7 GB 程度**しか必要にならず、
1 層保持で **19 GB には余裕**。これは sort/unique の作业メモリ（辺数分、
8.5 億 × 8 = 6.8 GB の sort buffer ＋ sort 作業領域）が障害の正体だったことを
裏付ける。
